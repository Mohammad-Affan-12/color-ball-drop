# Privacy implementation and submission worksheet

Status: prepared for owner review; no disclosure has been submitted and no policy has been published. Account and final build configuration determine the final answers. This document supersedes the older simulated-service assumptions in ASO_AND_RELEASE_GUIDE.md.

## Implemented behavior

- No account, login, email, contacts, GPS, camera, microphone, social SDK or backend save. Progress, preferences and entitlements remain local in the existing v2 ConfigFile save. Existing legacy `privacy_consent_granted=true` does not authorize either service.
- Separate optional analytics toggle starts **off** for new and migrated saves. The privacy panel explains the processor, purpose, event types, random local identity and IP-derived country before enabling. Turning it off cancels the request, clears queued/history events and deletes the local analytics ID. It does not claim to erase data already sent to a provider.
- `AnalyticsService` sends only allowlisted game/ad event names and app-defined properties over HTTPS to an explicitly configured PostHog regional ingestion host. A random pseudonymous install ID enables return measurement. This is **not fully anonymous**. Locale is not a country measurement. No event replay/video recording is enabled. Empty host/key means no transmission.
- `AdService` alone calls Google's UMP and AdMob APIs. It requests fresh consent information per app process at a safe menu/result break, shows required forms only if still at a safe break, and initializes/loads ads only after UMP returns NOT_REQUIRED or OBTAINED. SDK consent strings determine ad-serving eligibility; a game checkbox never supplies Google consent. Unknown/failure keeps ads unavailable. No forced form during active physics play.
- Settings → Privacy & data choices → Google ad privacy options remains reachable; the UMP privacy-options form is shown when required. The wrapper exposes consent status rather than `canRequestAds()`, so availability uses conservative fresh status gating. Recheck this mapping and all regulated geography cases on a device after account messages are configured.
- No mediation adapters were installed: only Poing's ads/core Android AARs. The plugin depends on GMA Next-Gen `ads-mobile-sdk:1.4.0`. UMP/native dependencies must be audited in the final resolved Gradle graph and merged manifest. No claim that SDK presence alone guarantees privacy compliance.
- The successful local build resolved UMP **4.0.0** and includes the consent/user-messaging plugin registrations in its merged manifest. Native runtime geography/consent acceptance is still a physical-device/account gate.
- Advertising remains disabled behind `release/ads/audience_reviewed=false` until the owner resolves target audience, child-directed and under-age flags. Conservative child/under-age defaults are not an age screen or a completed Families assessment. Do not set the flag merely to bypass this decision. If children are in scope, implement the required audience-specific flow and validate SDK eligibility before enabling ads/analytics. A mixed audience needs a reviewed neutral age flow rather than treating all players as adults.

## Data Safety answers to verify against final bundle

The successfully built debug APK was inspected with `aapt dump permissions`. Besides INTERNET, ACCESS_NETWORK_STATE and VIBRATE, dependency manifests add `android.permission.AD_ID`, `com.google.android.gms.permission.AD_ID`, `READ_BASIC_PHONE_STATE`, `WAKE_LOCK`, `FOREGROUND_SERVICE`, and an app-specific DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION. These are real merged declarations and must be included in the release dependency/audience audit; the game's export checkboxes alone are not the full manifest. READ_BASIC_PHONE_STATE permits basic network/software phone state, not phone-number permission; see [Android permission reference](https://developer.android.com/reference/android/Manifest.permission#READ_BASIC_PHONE_STATE). Do not claim the bundled SDK is identifier-free or make categorical “no permissions” marketing claims. No dangerous contacts/camera/microphone/GPS permission was present in that inspected manifest.

Disclose the **ad-enabled final distribution**, including all SDK behavior, even if play works offline and some users decline collection. “No data collected” is not an accurate blanket answer for a monetized build. Google states the Next-Gen SDK handles IP address, product interactions, diagnostics and device/account identifiers; use the exact version's documentation and resolved dependencies at submission. [GMA Next-Gen data disclosure](https://developers.google.com/admob/android/next-gen/privacy/play-data-disclosure).

Additional form questions: verify all SDK transport is encrypted in transit; do not infer that from the game's HTTPS alone. Determine optional vs required per data type, actual consent/serving behavior and whether a player can avoid the relevant collection. Do not claim “ephemeral” unless processing meets Google's definition; local in-memory event buffering does not make server data ephemeral. Determine sharing exemptions using the actual service-provider relationship and vendor terms, not guesswork. No account-creation deletion URL is required solely for local saves, but answer the current Play form accurately and provide a data-request contact for pseudonymous telemetry if used.
